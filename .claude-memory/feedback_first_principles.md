遇到连锁障碍时的反模式：**在错误路径上继续打补丁**。

**典型失败案例（git push 事件）：**
1. SSH 失败 → 改 HTTPS
2. HTTPS 认证失败 → 教用户建 PAT
3. PAT 通过但 push rejected → 教用户 rebase
4. Rebase 冲突 → 教用户改 README
5. 改完之前没 rebase 完就出现 unstaged changes → 又要教用户 stash

每一步看似合理，整体是**越走越深的兔子洞**。原本 30 秒的事变成 10 分钟来回截图。

**Why:** 解决表面症状会一层一层暴露新症状，而根因（本机没 SSH key）其实 2 分钟就能治本。继续打补丁对用户是认知负担，对我是错觉（"马上就好了"）。

**How to apply:**

1. **累计 ≥2 次意外障碍时强制 reconsider**
   - 不是 "再试一下就好"
   - 回到目标：用户要的**最终状态**是什么？
   - 现在这条路到目标的**剩余步骤**有几步？
   - 有没有**绕过所有残余问题**的直接路径？

2. **向用户显式提"换路径"选项**
   - 不要默认继续当前路径到底
   - 把"换路径 vs 继续修"的成本对比讲清楚，让用户选

3. **对 git/认证/部署这类状态机问题更敏感**
   - 状态机每错一步都会产生新状态（冲突、unstaged、stash…）
   - 每个新状态又可能再错一步
   - reset 到已知干净状态往往比前进便宜

4. **信号词**
   - "再试一下"、"快好了"、"只差一步" → **自己** 警觉
   - 用户说"感觉绕进去了"、"这个是不是更简单" → **立即停，重新评估**

5. **第一性原理提问清单**
   - 目标是什么（最短定义）？
   - 现在的状态是什么？
   - 中间有什么阻碍？
   - 最短路径绕过阻碍是什么？
   - 我是在解决阻碍，还是在解决**解决阻碍**过程中出的新阻碍？
