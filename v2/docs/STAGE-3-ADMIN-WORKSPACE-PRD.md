# Stage 3 MVP PRD: 管理后台收口

## 1. 目标

Stage 3 MVP 只解决一件事：

把现有 v2 后台能力整理成一个可以稳定上线的管理后台，同时把数据写入流程从 GitHub JSON 收到 D1 / API-first。

本阶段不做大改版，不引入复杂角色体系，不做学科负责人工作台。优先保证现在已经有的场景不丢。

## 2. MVP 范围

保留并整理三个后台场景：

1. 学科管理
   - 新建学科
   - 编辑学科
   - 删除空学科
   - 展示内容数量
   - 展示编辑者 / 只读者摘要

2. 用户权限管理
   - 继续使用“用户 × 学科”的权限矩阵
   - 每格权限只展示四种状态：`无`、`只读`、`编辑`、`ALL`
   - 支持按用户 / 邮箱搜索
   - 支持即时修改权限

3. API Tokens
   - 创建 Token
   - 选择关联用户
   - 选择学科范围
   - 选择有效期
   - 一次性展示明文
   - 撤销 Token

## 3. 不做什么

本阶段暂不做：

- `owner / editor / viewer` 产品角色体系
- 学科负责人自助后台
- 学科详情页
- 审计日志完整 UI
- 计费 / 订阅
- 复杂 API 使用诊断
- 可视化 API request builder
- 大规模批量导入器

这些可以作为后续阶段讨论，但不能进入本 MVP 的必做范围。

## 4. 角色与权限语言

MVP 使用当前 v2 已经存在、用户也能理解的语言：

| UI 文案 | 当前后端含义 | 说明 |
|---|---|---|
| 无 | 没有 `user_permission` 行 | 不能访问该学科 |
| 只读 | `user_permission.role = guest` | 可以看，不能写 |
| 编辑 | `user_permission.role = admin` | 可以读写该学科内容 |
| ALL | `ADMIN_EMAILS` 命中 | 超级管理员，全学科可读写 |

产品决策：

- 页面上不展示 `R` / `A`，直接写“只读”“编辑”。
- 页面上不展示 `owner`。
- 如果后端为了兼容 API-first 需要写 `tenant_member`，可以在服务端同步映射，但不要暴露成 MVP 产品概念。

## 5. 页面设计

### 5.1 学科管理

入口仍沿用当前后台里的“学科管理”。

列表每行展示：

- 学科中文名
- 英文名
- 备注
- 内容数量：视角、学派、学者、KP
- 编辑者摘要
- 只读者摘要
- 编辑按钮
- 删除按钮或“含内容”禁用态

交互规则：

- 新建学科按钮放在“学科列表”这一层。
- 新建 / 编辑表单字段：
  - 中文名
  - English
  - 日本語
  - 备注
- 删除只允许空学科。
- 有内容的学科显示“含内容”，不能删除。
- 不需要“配权限”按钮。权限主流程在“用户权限管理”里完成。

### 5.2 用户权限管理

保留 v2 的权限矩阵，因为它最适合回答这个问题：

“这个邮箱在哪些学科里分别是什么权限？”

矩阵结构：

- 行：用户
- 列：学科
- 单元格：`无`、`只读`、`编辑`
- 超级管理员显示 `ALL`，不可在页面里修改

交互规则：

- 点击单元格即可切换权限。
- 修改后即时生效。
- 用户展示优先使用短名，邮箱作为辅助信息。
- 长邮箱必须截断，不能撑开表格。

### 5.3 API Tokens

保留当前全局 Token 页面逻辑。

创建表单字段：

- 名称
- 关联用户
- 有效期
- 学科范围

规则：

- Token 权限不能超过关联用户已有权限。
- 不勾选学科范围时，Token 继承该用户全部学科权限。
- 勾选学科范围时，只能进一步收窄。
- 生成后只显示一次明文。
- 已有 Token 支持撤销。

列表展示：

- Token 名称
- 关联用户
- 学科范围
- 创建时间
- 过期时间
- 最近使用
- 撤销按钮

## 6. API 与数据要求

### 6.1 学科写入

MVP 要把学科创建 / 编辑 / 删除收口到 D1。

要求：

- `/admin/disciplines` 不再通过 GitHub Contents API 写 `v2/data/<discipline>/discipline.json`。
- 新建学科写入 D1 的 `discipline`。
- 如果当前后端仍需要 `tenant` 表，则服务端自动创建或同步。
- 删除只允许空学科。

### 6.2 权限写入

MVP 继续以 `user_permission` 作为产品主语义。

要求：

- `只读` 写入 `guest`
- `编辑` 写入 `admin`
- `无` 删除该用户该学科的权限行
- `ALL` 由 `ADMIN_EMAILS` 决定，不写入权限表
- 如果需要兼容 `tenant_member`，服务端同步写入即可

### 6.3 Token 写入

要求：

- Token 绑定用户
- Token scope 只能等于或小于用户权限范围
- Token 明文只展示一次
- 撤销使用软删除或 `revoked_at`
- 过期或撤销后 API 不可用

## 7. 验收标准

学科管理：

- 可以创建学科，线上立即可见。
- 可以编辑学科名称和备注。
- 空学科可以删除。
- 有内容学科不能删除。

用户权限：

- 可以看到所有用户和所有学科的权限矩阵。
- 单元格只出现 `无`、`只读`、`编辑`、`ALL`。
- 修改权限后刷新仍然保持。
- 超级管理员行不可被修改。

Token：

- 可以为某个用户创建 Token。
- 可以选择有效期。
- 可以选择学科范围。
- 不能给用户没有权限的学科生成 Token。
- 创建后只显示一次明文。
- 可以撤销 Token。

安全：

- 服务端不能相信前端传来的 `tenant_id`。
- 所有写入都必须基于当前登录用户和服务端权限判断。
- Token 不能放大用户权限。

## 8. 后续再说

后续阶段可以重新评估：

- 是否需要 owner 角色
- 是否需要学科负责人自助后台
- 是否需要审计日志 UI
- 是否需要 API quickstart 页面
- 是否需要按学科分组的成员管理页

这些不是当前 MVP 的一部分。
