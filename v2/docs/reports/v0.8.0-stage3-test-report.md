## 4. Findings

### F1 (P1, real bug, 已复现) — `kp-legacy-detector` 别名 hardcode 缺 `企业例`

**现象**：调用方 POST/PATCH 时，把 `◆企业例——苹果案例` 写到 `body.zh.prose`（narrative format），detector **不识别**为 `legacy_eval_in_body`，请求继续走 zod parse → 通过 → 写入 D1（新+旧列双写）。

**复现**：[T8.5 + T8.6](v2/tests/kps-v08-stage3-supplement.test.ts:858)

```bash
$ pnpm vitest run tests/kps-v08-stage3-supplement.test.ts -t "T8.5"
✓ T8.5 [F1 BUG 复现] body.zh.prose 含 ◆企业例—— → detector hardcode 缺此 alias，绕过拒绝写入
```

T8.6 一次性遍历 13 个 EVAL_DEFS alias，明确报告：

```
failed = ['example/企业例 (got 201 reason=undefined)']
```

其余 12 个 alias（`意义/意義/局限/限界/例子/例/应对/應對/应用/應用/比喻/譬喩`）全部正确返 `legacy_eval_in_body` 422。

**根因**：[v2/src/lib/kp-legacy-detector.ts:101-108](v2/src/lib/kp-legacy-detector.ts:101)

```ts
// 注释（撒谎）：
// 注意：使用了 EVAL_DEFS 的别名集合（保持单一真源），所以 EVAL_DEFS
// 加新别名时这里自动跟。
const LEGACY_EVAL_MARKER_PATTERN = (() => {
  const aliases = [
    '意义', '意義', '局限', '限界', '例子', '例',
    '应对', '應對', '应用', '應用', '比喻', '譬喩',
  ];
  return new RegExp(`◆\\s*(${aliases.join('|')})\\s*—{2,}`);
})();
```

跟 [v2/src/lib/body-parser.ts:42-48](v2/src/lib/body-parser.ts:42) 的 `EVAL_DEFS` 对比：

| EVAL_DEFS key | EVAL_DEFS aliases | detector hardcode | diff |
|---|---|---|---|
| meaning | 意义 / 意義 | 意义 / 意義 | OK |
| limit | 局限 / 限界 | 局限 / 限界 | OK |
| **example** | **例子 / 企业例 / 例** | **例子 / 例** | ❌ 缺 `企业例` |
| response | 应对 / 應對 | 应对 / 應對 | OK |
| application | 应用 / 應用 | 应用 / 應用 | OK |
| analogy | 比喻 / 譬喩 | 比喻 / 譬喩 | OK |

EVAL_DEFS 13 alias / detector 12 alias / **缺 1 个**。

**影响**：
- PRD §4.3 + migration §4.3 明确"body 内禁止 ◆评价—— 段，必须独立写到 evaluations 字段"
- 当前 hard cut **能拦 12/13** — 老师 agent 用 `◆例子——` 或 `◆例——` 都会 422，但用 `◆企业例——` 会通过。
- v0.7.x 数据中是否大量存在 `◆企业例——` 写法？— v0.7.41 backfill report 显示 692 KP / 0 errors，应已迁移，但**调用方代码若复用旧模板**仍可能写新数据。

**建议修法**（5 行 patch）：

```ts
// kp-legacy-detector.ts
import { EVAL_DEFS } from './body-parser';

const LEGACY_EVAL_MARKER_PATTERN = (() => {
  const aliases = EVAL_DEFS.flatMap((d) => d.aliases)
    .map((a) => a.replace(/[.*+?^${}()|[\]\\]/g, '\\$&'));
  return new RegExp(`◆\\s*(${aliases.join('|')})\\s*—{2,}`);
})();
```

这就真兑现注释承诺的"单一真源"。无新依赖、无 schema 改动。

**严重程度判断**：P1 但**不阻塞 ship**。理由：
- 误判方向是"漏拒"而不是"误拒"，调用方写错也能写入数据，再迁移可控
- 写入的数据仍合法 KpBody，不会让渲染崩
- staging 测试会（5/12）老师 agent 用真实工作流，可发现并 IM
- 修法 5 行；可单独 PR 合到 v0.8.0 ship 之前

### F3 (P2) — 顶层 `body` 是 string（非 `{zh, ja}` object）→ 不归 `legacy_string_body`

**现象**：调用方传 `body: "plain DSL string"` 顶层（旧 v0.7.x 一些 callsite 可能这样），detector 跳过 string body 检查（其检查只在 `typeof p.body === 'object'` 时跑），直落 zod → reason `body_structure_invalid`。

**复现**：[T8.7](v2/tests/kps-v08-stage3-supplement.test.ts:932)

```ts
body: 'plain string at top level'  // 不是 { zh, ja }
// → got reason: 'body_structure_invalid'
// → 期望 reason: 'legacy_string_body'
```

**根因**：[kp-legacy-detector.ts:65-73](v2/src/lib/kp-legacy-detector.ts:65)

```ts
if ('body' in p && p.body && typeof p.body === 'object') {
  // ... 检查 body.zh / body.ja 是 string
}
// 漏掉：body 顶层是 string 的情况
```

**影响**：调用方收到的 reason 不最准（migration_guide URL 仍带，可定位）。属于 user-experience 小瑕疵，不影响功能。

**建议**：detector 加分支：

```ts
if ('body' in p && typeof p.body === 'string') {
  return { reason: 'legacy_string_body', message: '...' };
}
```

不阻塞 ship；可在 v0.8.1 跟。

### F4 (P3) — `classifyZodFailure` 把非 body 字段错归 `body_structure_invalid`

**现象**：当 zod fail 在 schools / title / id 等非 body 字段时，[`pathTouchesBodyFormat`](v2/src/lib/kp-legacy-detector.ts:140) 默认 false → reason 是 `body_structure_invalid`，但实际错跟 body structure 无关。`detail.issues` 有完整 zod path/message 可定位。

**复现**：T6.3（KpId regex 不匹配）— Dev 写测试时也用 `body_structure_invalid` expect，是 known behavior。

**影响**：调用方 reason 不准；`detail` 可救。

**建议**：默认归 `schema_invalid`，仅 path 触及 body 时归 `body_structure_invalid`。需 migration-v0.8.md §7 表格新增一行 `schema_invalid`。

不阻塞 ship。

### F5 (P2) — schema 允许 `body.zh.format != body.ja.format`，旧列 `format` 只跟 zh

**现象**：[KpBodyBilingual](v2/src/schemas/kp-api.ts:32) zod 允许 zh/ja 各自独立选 format（migration §FAQ Q4 说"产品上强制一致，schema 允许灵活"）。但 [deriveDualWriteCols](v2/src/lib/kp-api-store.ts:66) 旧列 `format` / `body_format` 都只记 `body.zh.format`。

**复现**：[T2.2](v2/tests/kps-v08-stage3-supplement.test.ts:178)

```ts
body: { zh: NARRATIVE, ja: FLAT_LIST }  // schema 通过
// → body_format = 'narrative'（只跟 zh）
// → body_zh_json = {format: narrative, prose: ...}
// → body_ja_json = {ja, format: flat-list, ...}
// 新列没问题，旧 format 列在 ja 那一面信息丢失
```

**影响**：
- v0.7.x 老 reader（如果还有）只能看到 zh format，ja 那面看不到 — 但 v0.7.39 起渲染层已切新列，此问题仅当回滚到旧 reader 才暴露。
- Stage 5 drop 旧列后此问题消失。
- 老师 agent 若按文档"产品上强制一致"行事，永远不踩。

**建议**：选其一
1. schema refine：`zh.format === ja.format` 强制
2. 文档明示这是已知 corner case + UI 永远同步切（编辑器侧）
3. 不动（可接受，Stage 5 后无意义）

不阻塞 ship。
